# FIELD COMMAND / 戦線指揮（SRPG） のPR監督

正本は `CLAUDE.md` → `AGENTS.md` / `docs/DEVELOPMENT.md`。このスキルはそれを実行する手順で、矛盾したら正本が勝つ。
2026-10-21からはノンストップ試作フェーズ（下の「毎日15時の昼ラン」）。独立レビューと実機試遊は夕方の試遊にまとめ、未実施は未実施と記録する。highの変更はPR本文に短い技術設計を書いてから実装する。現行ルールは `docs/hp6-campaign-design.md`（v0.8.0）。

## 権限の境界（どのPRでも同じ）

- mainへ直接push・force-push・rebaseによる履歴の書換え・GitHubのauto-merge機能・PRの承認(Approve)をしない。マージは「毎日15時の昼ラン」だけが条件付きで行い、それ以外の巡回・セッションではマージしない。
- GitHubのSettings・Ruleset・Secrets・Pages設定・リポジトリ名・表示名・保存キーを変えない。
- 他の人やAIのブランチを直すときは、最新mainを **merge commit** で取り込む（rebase・amendしない）。
- 承認されていない仕様（新しいマップ・数値・演出・物語・ルール・課金・保存）を、PRの「ついで」で足さない。必要なら提案Issueを書いて人間に返す。
- トークン・個人のチャット・ローカルのスクリーンショットや `test-results/` をコミットしない。

## 1本のPRを監督する手順

1. **現在地**：`git fetch origin`、PRのhead SHA・base・対応Issue・作成者（Codex/GPT/人間/Claude）を確認。Issueが無い・採用根拠が書かれていないPRは、コメントで「採用根拠の確認待ち」と人間に返し、仕様の中身を推測で補わない。
2. **競合**：mainと競合していれば、PR headへmainをmergeして解消し、関係するテストを再実行してからpush。両側が同じロジックを変えて片方の振る舞いを失う場合は、直さず人間へ質問。
3. **CI**：`rules` / `browser`（このrepoのジョブ名は下）を確認。赤ければ原因をこのPRの差分の中で特定して直す。「たまたま失敗」は原因にしない。再実行は1回まで。テストのスキップ・削除・弱体化で緑にしない。
4. **差分の監査**：下の「リスクの見分け方」で low/medium/high を決め、AGENTS.mdの不変条件を1つずつ照合する。PR本文は作成者の主張であって検証済みの事実ではないので、コード・テスト・Git履歴で確かめる。独立かどうかは**セッション単位**で判断する。Codex/GPT/人間が書いたPR、またはコミットやコメントにある `Claude-Session:` のURLが今のセッションと違い、このセッションが実装に関わっていないPRなら、このレビューを**独立監査**として記録できる。今のセッションで書いたコミットを含むPRでは「自己確認」と書き、独立監査と呼ばない。
5. **直してよい範囲**：CI失敗・明白なバグ・テスト追加・誤字・PRの目的の範囲内の小修正は、そのPRのブランチ（このリポジトリ内のブランチに限る。forkには触らない）へpushしてよい（2026-10-20、はねさんが「朝までに反映・実装」を希望し、方針をClaudeに委任）。
   - pushの前に、下の「このrepoの検査」を全部実行して成功を確かめる。CIの修正なら、先に元の失敗を再現する。
   - 1つのPRにつき、1回の巡回でpushするのは検証済みの1回まで。そのpushでもCIが赤いままなら、それ以上は触らず、原因と修正案をコメントに書いて人間へ返す。
   - 設計を変える提案（ファイル横断のリファクタリング、仕様・数値・API・保存形式の変更）や、危険度highの箇所の書き換えは、pushせずコメントで提案し、人間かPR作成者の判断を待つ。
6. **記録**：PRへ1件のコメントで、次の形で残す（PASS/WARN/BLOCKは報告語で、CIや人間承認の代わりにならない）。

```
## Claude監督レビュー
- 判定：PASS / WARN / BLOCK（リスク：low/medium/high、独立監査 or 自己確認）
- 対象SHA：<sha>
- 実行したテスト：<コマンドと結果>
- 不変条件の照合：<破れていない/破れている項目>
- 直したこと：<push したコミット、なければ「なし」>
- 未検証：iPhone実機・WebKit・実耳 など
- 人間に決めてほしいこと：<なければ「なし」>
- 試遊項目：<iPhoneで見る操作>

---
_Generated by [Claude Code](https://claude.ai/code)_
```
最後の3行（空行・`---`・署名）は、GitHubに書くコメントには必ず付ける。

7. **引継ぎ**：PRが人間の判断待ちになったら、それ以上の変更はしない。同じhead SHAに「Claude監督レビュー」が既にあり、それ以降にmain・CI・レビューが変わっていなければ、新しいコメントを書かない（二重投稿をしない）。

## 毎日15時の昼ラン（ノンストップ試作フェーズ、2026-10-21〜）

はねさんが昼休みに投げたIssue・PRを、夕方に遊べる状態でmainへ入れるための手順。対象は `hane-san/ARPG-02-retrostyle` と `hane-san/SRPG-01-FEstyle` の2つ。15時ごろに始め、18時ごろまでに終える。**この節の中に限り、上の「権限の境界」のうちマージの禁止は解除される**（Approve・auto-merge機能・main直push・force-pushは引き続き禁止）。

0. **準備**：両repoを `git fetch origin`。そのランに指定された作業ブランチを使う（前回のPRがマージ済みなら、最新mainから同じ名前で作り直す）。`npm run check` で基準を確かめる。
1. **棚卸し**：両repoの開いているPR・Issue・mainのActionsを一覧にし、各項目を「採用済み／提案／hold」に分ける。持ち主のアカウント（GPT・Codexの代理を含む）が作ったものは採用済み。タイトルが「提案」で始まる・本文に「未採用」「保留」「マージ保留」・`hold`/`proposal` ラベルのものは提案かhold扱いで、実装もマージもしない。
2. **既存PRから**：古い順に、上の手順1〜6（競合→CI→監査→修正→記録）。採用済みでマージの条件を満たしたらマージする。Draftでも採用済みならReadyにしてよい。同じファイルで衝突する複数PRは、作業ブランチへmerge commitで統合して1本のPRにし、元のPRには統合先を書いてから閉じる。
3. **採用済みIssueの実装**：優先順は、遊べない不具合→採用済みの機能→操作・描画・音の改善→テスト・保守。大きいものは遊べる単位に分けてPRにし、動く部分から順にマージ。全部終わったIssueは `Closes #n` で閉じ、途中ならIssueに残りを書く。
4. **マージの条件**（最新のhead SHAで全部）：`rules` / `browser` 成功、最新mainと衝突なし、このランの監査でBLOCKなし、`hold` ラベルなし。PRの通常のmerge commitでマージする。
5. **マージ後**：mainのActionsとPagesのデプロイが成功したかを確認し、公開URLをChromiumで開いて起動とpageerrorなしを確かめる。壊れていたら、同じランでrevert PRを作ってマージする。
6. **記録**：各repoの「昼ランの記録」Issue（なければ作る）に1日1件、次をコメントする：マージしたPRとSHA、実行したテスト、未検証（iPhone実機・聴感・独立監査）、夕方に試してほしい点、残件、はねさんに決めてほしいこと。最後の返答も同じ内容を短く。
7. **詰まったら**：1件に30分以上かかったら、原因と次の手をPRかIssueに書いて次へ進む。ゲートを満たさないものはマージしない。テストを消す・弱めるのは禁止。

独立監査について：GPT・Codex・人間が作ったPRをこのランで見るのは独立監査。このランが自分で実装した差分は自己確認なので、「独立監査は未実施」と記録する。
SRPGの追加：ルール・数値・マップを変えたら `npm run simulate` を実行して結果をPRに書く。保存形式を変えるなら同じPRに移行テストを入れる。変更したモジュールの読み込み `?v=` タグを更新して、Pagesで古いキャッシュが残らないようにする。

## 夜間巡回（スケジュール実行で使うとき）

1. 開いているPRを古い順に全部見る。各PRで上の手順1〜7。1PRの作業が長引いても、他のPRの状態確認は必ず済ませる。
2. 開いているPRが無い・全部が人間待ちなら、`docs/ROADMAP.md` の未完了項目（`[ ]`）とIssueのうち、**人間が採用済みと明記したもの**だけを1件選び、`claude/<issue>-<topic>` ブランチ→PRで進める。採用済みが無くても、既存の仕様どおりに動かない明白な不具合（重なり・押せない・エラー・テストの穴）は、Issue→修正PRにしてよい。新しい体験・仕様の思いつきは「提案Issue」に留め、実装しない。
3. 朝の報告は、PRごとに「判定・対象SHA・直したこと・人間に決めてほしいこと・試遊項目」を1行ずつ。成功していないものを成功と書かない。GitHubに接続できないなど途中で止まったら、どの段階で何が失敗したかを書いて終える。
4. 夜間巡回では、定期タスクの作成・変更、他のリポジトリの操作、関係のないコネクタの操作をしない。

## このrepoの検査

CIのジョブ：`SRPG rules` の `rules` / `browser`

```sh
npm run check                        # 構文 + 決定論ルールテスト
npm run simulate                     # ルール・数値・マップを変えたら前後比較
python3 -m http.server 4173 &        # ブラウザ検査はこのサーバーを使う
npm run test:browser                 # クラウドではSessionStartフックがCHROMIUM_EXECUTABLEを用意
```
版を上げるときだけ `node scripts/release.mjs X.Y.Z`。docsだけの変更では版を上げない。

## リスクの見分け方

| リスク | このrepoでの例 |
|---|---|
| low | docs、文言、`config.js` の説明文だけ |
| medium | `app.js` / `style.css` / `ui-input.js` / `ui-model.js` / `playback.js` / `render.js` のUI・演出、`audio.js` / `music*.js`、`data.js` の個別マップ |
| high | `engine.js` の4フェーズ・戦闘ルール、`save.js` の保存互換、`config.js` の数値（バランス）、横断する状態 |

## 監査で必ず照合する不変条件（要約。詳細はAGENTS.md）

- P1味方→P2敵→P3支援→P4予告。命中乱数なし、決定論。全ユニットmaxHP6などHP6契約。
- 公開コマンドは攻撃/待機のみ、確認ステップを増やさない。経路は `engine.routeTo` と同じ重み。
- 命令欄は盤面外の固定高さ。選択・取消でカメラ・盤面寸法を動かさない。44pxのタッチ領域。
- v0.8の保存を壊さない、旧保存は安全に失敗。FEの画像・音・キャラを使わない。
